# 🚀 Upserve – Complete Project Documentation

## 1. Project Overview

**Project Name:** Upserve Backend

**Purpose:** A software-agency management API covering client intake, CRM, requirements, quotations, projects, collaboration, deliverables, invoices, blogs, and portfolio content.

**Technology:** FastAPI, Python, MongoDB, Motor, JWT, Pydantic, Resend, and ReportLab.

Upserve is a production-oriented MVP. It centralizes the agency workflow without claiming to be a complete accounting, messaging, storage, or identity platform.

## 2. Complete Business Workflow

```text
Client account / contact intake
          │
          ▼
Lead creation and assignment
          │
          ▼
Requirement creation and approval
          │
          ▼
Quotation creation, revision, and sending
          │
          ▼
Client accepts quotation
          │
          ▼
Project creation and initialization
          │
          ▼
Project execution: deliverables, timeline, discussions, files
          │
          ▼
Project delivered
          │
          ▼
Invoice generated and sent
          │
          ▼
Payment confirmed
          │
          ▼
Project completed
```

Quotation acceptance creates the project automatically. Repeated acceptance/recovery calls reuse the existing project when it can be found and reinitialize only missing secondary records.

## 3. Architecture

```text
HTTP Request
     │
     ▼
FastAPI API Routers
     │  authentication and request validation
     ▼
Service Layer
     │  business rules, authorization, lifecycle orchestration
     ▼
Repository Layer
     │  MongoDB queries, indexes, conditional updates
     ▼
MongoDB
```

### API layer

The routers are under `app/api/`. They authenticate requests, validate request bodies with Pydantic, apply coarse role checks, and map application exceptions to HTTP responses.

### Service layer

The services under `app/services/` contain the business workflow. Services repeat important authorization and active-user checks so that internal service call paths do not rely only on router checks.

### Repository layer

The repositories under `app/repositories/` isolate MongoDB access. They register indexes during application startup and provide conditional updates for status and payment transitions.

### Supporting areas

- `app/db/database.py`: MongoDB client and database selection
- `app/db/models.py`: password hashing and password verification helpers
- `app/db/schemas.py`: request and response models
- `app/config.py`: environment configuration and upload rules
- `app/exceptions.py`: application exceptions and HTTP mapping
- `app/main.py`: startup initialization, index registration, and router inclusion

## 4. Authentication and User Management

### Login

`POST /api/auth/login` validates the normalized email and password, rejects inactive users, and returns a JWT containing the authenticated identity information. Only supported database roles are accepted:

```text
super_admin
sub_admin
client
```

### Database-backed authentication

The JWT is not the final authority for account state or authorization. Current-user resolution loads the user from MongoDB and verifies:

- the user still exists;
- the account is active;
- the database role is supported;
- the token security version matches the current user security version.

Missing, deleted, inactive, malformed, expired, invalid-signature, and unsupported-role tokens produce controlled authentication errors. Legacy users without newer security fields use conservative defaults where supported.

### Password lifecycle

- Passwords are stored as hashes, never plaintext.
- Password changes require the authenticated user and increment the security version.
- Existing tokens are invalidated after security changes.
- Generated Sub Admin accounts receive a temporary password and `mustChangePassword=true`.
- The password-change flow clears the forced-change state.

There is no password-reset, MFA, OAuth, refresh-token, or email-verification subsystem.

### User creation and status

- Clients can be created through the existing client-creation flow.
- Super Admins can create Sub Admins.
- Sub Admin credentials are generated by the server.
- Super Admins can activate or deactivate users.
- Email values are normalized before lookup and creation.
- Database uniqueness and duplicate-key translation protect user email uniqueness.

## 5. Authorization and Roles

Authorization is the combination of role checks and resource ownership/assignment checks.

### Super Admin

Super Admins can manage users, leads, requirements, quotations, project lifecycle/budget, invoices, blogs, portfolio content, and global administration functions. Important operations such as project status changes, invoice operations, requirement approval, timeline deletion, and lead assignment require an active database-backed Super Admin where enforced by the service.

### Sub Admin

Sub Admins can work only within their authorized lead/project scope. Their access is based on assignment to a lead or project; the role alone does not grant access to all agency data.

Sub Admins cannot approve requirements, change project status or budget, send/confirm/cancel invoices, or assign leads to arbitrary users.

### Client

Clients can access only their own projects and related authorized resources. They can review and act on their quotations, participate in project discussions, view client-visible files and deliverables, and view their invoices. Client input cannot provide a trusted sender identity, role, payment confirmation, or arbitrary ownership relationship.

### Module-specific restrictions

- Lead history is protected by lead access.
- Requirements are protected by lead/project access; clients can submit and revise their own requirements until approval.
- Quotation PDF downloads authorize through quotation access and generate the latest detailed PDF from stored quotation data.
- Discussions are protected by project access; system messages cannot be deleted.
- Upload downloads authorize through the upload's actual project.
- Invoice access and downloads authorize through the invoice's project.
- Notifications can be read, marked, or deleted only by their recipient.
- Activity-log access is restricted by the activity API policy; activity records are append-only.

## 6. CRM Leads

Leads are normalized by email and receive an initial `New` stage. When a Sub Admin creates a lead, it is automatically assigned to that Sub Admin and the assignment is recorded in lead history.

Lead assignment is controlled through the dedicated Super Admin assignment flow. Assignments must target an active Sub Admin; clients, Super Admins, nonexistent users, and arbitrary users are rejected.

The supported lead stage flow is validated by the service. Won and Lost are terminal for ordinary lead stage actions. Lead history records changes, actor, timestamps, and assignment information.

Lead conversion can reuse an existing client account matching the lead email or create a client account through the current user/client architecture. The flow does not create duplicate users for an existing client email.

---

## 7. Requirements

Requirements must reference a valid lead or project. When both are supplied, they must belong to the same business flow. Existing lead/project relationships and client ownership are validated before creation.

Requirement states are:

```text
PENDING → APPROVED
PENDING → CHANGES_REQUESTED
CHANGES_REQUESTED → APPROVED
```

Clients submit and can revise their own requirements until approval. Super Admins approve requirements or request changes. Approved requirements cannot be edited or deleted through ordinary flows; changes must be requested before revision.

Each requirement may include one optional supporting attachment. The backend accepts PDF, JPG/JPEG, PNG, WEBP, DOC/DOCX, XLS/XLSX, PPT/PPTX, TXT, CSV, and ZIP files up to `MAX_UPLOAD_FILE_SIZE` (10 MB by default). Executable/script formats are intentionally rejected. Uploads are stored with collision-safe UUID filenames under the configured upload root, while the original name, content type, size, and upload timestamp are returned as metadata. Uploading a replacement removes the previous stored attachment.

The client uploads the file after the requirement record is created through `POST /api/requirements/{requirement_id}/attachment`. Authorized Super Admins can access the requirement and download the attachment through `GET /api/requirements/{requirement_id}/attachment`, including from the lead requirement panel. Approval remains a Super Admin-only action; Sub Admins can access attachments only within their assigned lead/project scope and cannot approve.

Requirement mutations record actor, role, timestamp, relationship identifiers, and changes in history. The initial creation history entry is embedded in the same MongoDB insert as the requirement, so a successful creation cannot leave the requirement without its creation history because of a second-write failure.

Requirements are frozen once implementation has started for the related project. Delivery/completion validation requires the related requirement to be approved when one exists.

## 8. Quotations

Quotation creation validates:

- the client exists and has the client role;
- lead, project, and client relationships are consistent;
- related requirement context, when present, belongs to the same lead/project relationship; requirements are optional;
- quotation items and totals are valid.

Totals are calculated server-side. Client input cannot safely replace the calculated total.

Quotation states include Draft, Sent, Viewed, Accepted, Rejected, Revision Requested, and Expired. The service validates transitions and the repository performs status changes conditionally on the expected previous state. Concurrent accept/reject/revision requests therefore cannot all succeed.

Client rejection is a terminal state for that quotation only. It does not mark the related lead as Lost. The lead remains available for explicit Admin lifecycle management, and a new quotation may be created for the same lead/project while rejected quotation records remain available as history. Active non-rejected quotation relationships remain protected against duplicates.

Quotation emails include a generated detailed PDF containing client details, quotation metadata, line items, quantities, prices, totals, timeline, validity, terms, and notes. Authorized users can also download the latest PDF through `GET /api/quotations/{quotation_id}/pdf`.

Acceptance is restricted to the quotation's client. An accepted quotation creates a project with client, lead, quotation, title, description, budget, and initial pending status. Existing-project recovery is idempotent for current records and supports legacy projects whose `quotationId` is stored as either a string or a MongoDB ObjectId.

After acceptance, an associated valid non-terminal lead is reconciled to `Won`. Missing, mismatched, or terminal invalid lead relationships are not overwritten.

## 9. Projects

### Lifecycle

```text
pending → in_progress → testing → deployment → delivered → completed
```

Only the next valid state is accepted. Project status and progress are separate concepts.

Project status updates are available to authorized Super Admins and Sub Admins and use an atomic expected-status update. If another request changes the status first, the losing request receives a controlled state-change error. If the status already changed successfully but its stable timeline event is missing, a retry recovers that event without treating the retry as a new status transition.

### Delivery and completion rules

Before `delivered` or `completed`:

- at least one deliverable must exist;
- every non-cancelled deliverable must be completed;
- if a related requirement exists, it must be approved; projects without a requirement are also valid.

Before `completed`:

- the project must already be `delivered`;
- a related invoice must exist;
- the invoice must be paid.

Invoice payment does not automatically complete a project.

### Derived project progress

Project responses include:

- `progressPercentage`
- `totalDeliverables`
- `completedDeliverables`
- `cancelledDeliverables`

The calculation is:

```text
completed non-cancelled deliverables
------------------------------------ × 100
total non-cancelled deliverables
```

Cancelled deliverables are excluded from the numerator and denominator. A project with no non-cancelled deliverables has `progressPercentage=null`. Progress is calculated from current deliverable records and is not manually stored in MongoDB. Reaching 100% does not change project status automatically.

### Project deletion

Project deletion is protected when related requirements, deliverables, timeline events, uploads, discussion messages, or invoices exist. This prevents orphaned business records and does not perform cascading deletion.

## 10. Deliverables

Deliverables belong to an existing project and are available only within the caller's project authorization scope. Clients can view client-visible deliverables; administrative changes are restricted according to the service rules.

Deliverable states are:

```text
pending → in_progress → blocked → in_progress
pending/in_progress/blocked → completed
pending/in_progress/blocked → cancelled
```

Completed and cancelled deliverables cannot be modified through the normal update flow. Status updates use conditional expected-status writes. Repeated completion requests can recover a missing completion timeline event without recording a second logical completion.

Active deliverable title uniqueness is protected per project through a MongoDB index for supported active statuses. Legacy deliverables with string or ObjectId `projectId` values are included in listing, progress, delivery validation, and completion validation.

---

## 11. Timeline

Timeline events are associated with projects and can be client-visible or internal. System events include project creation, lifecycle transitions, budget updates, and deliverable completion where applicable.

Lifecycle events use stable event keys and idempotent creation. If the project status write succeeds but event creation fails, repeating the same logical status operation recovers the missing event. System timeline events cannot be deleted through the normal delete flow.

Timeline retrieval supports legacy string/ObjectId project references. Client responses filter out internal and deleted events where applicable. There is no real-time timeline stream or WebSocket layer.

---

## 12. Discussions

Discussion messages are associated with projects and are visible only to authorized project participants:

- Client: own project only;
- Sub Admin: assigned/authorized project only;
- Super Admin: unrestricted project access.

New messages store `authorId`, `authorName`, and `authorRole` from the authenticated user. These values are not trusted from the request body. Replies are stored as part of the message document and returned through the response model.

Messages use soft deletion with `isDeleted`, `deletedAt`, and `deletedBy`. Deleted content is not exposed normally. System initialization messages are marked with `isSystemMessage` and cannot be deleted.

Initialization checks support both string and ObjectId project references, promote recognizable legacy initialization messages, and use the database uniqueness protection for concurrent current-record retries. Messages are ordered by `createdAt` descending and `_id` descending for stable pagination.

There is no real-time chat, WebSocket, read-receipt, or message-editing subsystem.

---

## 13. File Uploads

Uploads are project-level records containing metadata such as original name, stored name, project, uploader, role, content type, size, visibility, and timestamp.

### Authorization

- Clients can upload and view files only for their own projects.
- Sub Admins can access only authorized projects.
- Super Admins can access all project files.
- Client uploads are always client-visible; administrative uploads can use the visibility flag.
- Download authorization uses the upload ID and the upload's actual project association.

### Validation and storage

- Allowed extensions are configured in `app/config.py`.
- The default maximum file size is 10 MB and can be configured with `MAX_UPLOAD_FILE_SIZE`.
- Empty files are rejected.
- Filenames are sanitized and stored filenames use UUIDs.
- The configured `UPLOAD_STORAGE_ROOT` is created as needed.
- Physical paths are removed from normal API responses.
- If metadata creation fails after physical storage, the physical file is cleaned up.
- Deletion temporarily moves the physical file; if metadata deletion fails, the file is restored.

The system uses local filesystem storage. It does not provide cloud storage, antivirus scanning, or deep MIME/content inspection. A legacy Super Admin filename download route remains available, but authorization is still checked against the associated project.

## 14. Invoices and Payments

### Lifecycle

```text
generated → sent → paid
generated → cancelled
sent → cancelled
```

Paid and cancelled invoices are terminal. Projects use exactly three invoice stages: Advance, Milestone, and Final. Each project may configure positive stage percentages totaling exactly 100%. Projects without a stored schedule use the legacy-compatible 40/30/30 default. Authorized project editors can configure the schedule only before the first invoice is generated; existing invoice amounts are never recalculated.

Invoice generation is Super Admin-only and requires:

- a delivered project;
- deliverables;
- an accepted quotation;
- matching client, project, lead, and quotation relationships;
- a positive finite quotation total.

The invoice stores a snapshot of the accepted quotation amount. Later quotation changes do not recalculate an existing invoice.

Invoices are linked to the project, client, quotation, and lead where available. A unique project invoice rule and unique invoice-number index prevent duplicate current invoices. Duplicate-key failures are translated into controlled application errors.

### Payment stages and confirmation

The stage prerequisites are:

```text
Advance → paid Advance → Milestone → paid Milestone →
Delivered project → Final → paid Final → Completed project
```

Each invoice amount is calculated server-side from the accepted quotation value and that project's configured stage percentage. Stage uniqueness and exact payment validation remain enforced.

Payment confirmation is restricted to an active Super Admin and requires a sent, unpaid invoice for a delivered project. The payment amount must match the invoice amount and the request must include:

- `paymentAmount`;
- `paymentReference`;
- `paymentMethod`.

The atomic payment update stores `paidAt`, `paidOn`, and `paidBy`, and changes the invoice to `paid`. Repeated payment confirmation fails safely. There is no full accounting ledger or payment gateway integration.

### Sending and recovery

Invoice sending uses `emailSendState` as a persistent claim. A request claims a generated, unpaid invoice before sending. Failed delivery releases the claim. Successful delivery is followed by a conditional database transition to `sent`, preventing cancelled or paid invoices from being revived.

If the process fails while the result is uncertain, an active Super Admin can use:

```text
POST /api/invoices/{invoice_id}/reconcile-send
```

The endpoint only reconciles a stale generated/unpaid invoice whose send state is `sending` and whose timestamp is old enough. It records the reconciliation actor and timestamp, changes the state to `failed`, and does not automatically resend the email. Exactly-once external email delivery cannot be guaranteed.

### Access and downloads

Clients can view only invoices for their own projects. Admin access remains project-authorized. Invoice downloads are authorized by invoice/project relationship and return a file response without exposing the stored filesystem path.

## 15. Notifications

Notifications belong to a recipient. Users can list, mark, and delete only their own notifications. Recipients must be valid supported-role users; inactive recipients do not receive new notifications.

Notification lists use deterministic ordering. Indexes cover recent, unread, and event-key queries. Where an event key is provided, the unique event-key index and duplicate handling prevent repeated notifications for the same logical event.

Notification creation is best-effort for core business operations. Notification failures are logged and do not roll back a successful lead, project, invoice, discussion, or deliverable operation. There are no queues, push notifications, WebSockets, or background workers.

---

## 16. Activity and Audit Logs

Activity logs are append-only. Repository update and delete operations reject modification. Entries contain normalized actor identity/role, action, entity, entity ID, details, and an explicit UTC timestamp.

Legacy records using `createdAt` can be normalized through the timestamp fallback used by the service. Supported queries include:

- all logs for authorized administrative views;
- logs for a user;
- logs for an entity with optional entity filtering.

Indexes support timestamp ordering, user history, and entity history. Activity logging is best-effort: a log-write failure is recorded server-side and does not intentionally fail the core business operation. The system audits many important business actions, but it does not claim that every internal operation has an audit entry.

---

## 17. Database Integrity and Legacy Compatibility

Indexes are registered during startup for the current collections. Important protections include:

- normalized unique user email constraint with a searchable lead-email index;
- one requirement per supported lead/project relationship;
- active quotation/project relationship protection; rejected quotation history can coexist with a replacement quotation;
- active deliverable title uniqueness per project;
- one keyed current system timeline event per project;
- one current system discussion initialization message per project;
- unique stored upload filenames;
- one invoice per project and unique invoice numbers;
- notification event-key uniqueness;
- deterministic activity and notification ordering indexes.

Application-level validation and database indexes serve different purposes. A service check alone is not presented as a database constraint.

Targeted repositories accept string and ObjectId relationship values for legacy deliverables, timelines, discussions, uploads, requirements, invoices, and quotation-to-project recovery where implemented. Existing legacy records remain readable without automatic migration.

Project deletion checks for requirements, deliverables, timelines, uploads, discussions, and invoices before deletion. The backend does not automatically cascade-delete, migrate, or destructively clean up related records.

## 18. Error Handling and API Behavior

The application uses centralized exception mapping for expected failures, including:

- authentication errors;
- authorization errors;
- validation errors;
- duplicate records;
- missing resources;
- malformed identifiers;
- controlled state conflicts.

Unexpected/database/infrastructure failures produce a generic 500 response and are logged server-side. Raw database details, password hashes, and internal filesystem paths are not returned to normal API consumers.

Pydantic response models expose normalized identifiers and derived project progress while preserving backward-compatible defaults for legacy records where supported.

## 20. Configuration and Local Run

Required environment values include MongoDB connection, database name, JWT secret, Super Admin bootstrap credentials, Resend values, and explicit CORS origins. Optional operational values include JWT expiration, upload root, and maximum upload size.

```bash
python -m venv venv
venv\Scripts\activate       # Windows
# source venv/bin/activate   # Linux/macOS
pip install -r requirements.txt
uvicorn app.main:app --reload
```

The default local API address is `http://localhost:8000`.

Never commit real secrets or credentials. The application validates required configuration during startup.

## 21. Current Limitations

- External email cannot provide an exactly-once guarantee; manual invoice send reconciliation is intentionally conservative.
- Local filesystem storage requires persistent/shared storage for multi-instance deployment.
- Payment handling is a controlled full-invoice confirmation flow, not a gateway or accounting system.
- There are no background workers, queues, WebSockets, push notifications, MFA, password reset, OAuth, refresh-token, or cloud-storage features.
- Legacy compatibility is targeted and does not replace a formal migration process.

---

## 22. Project Summary

Upserve connects the core software-agency workflow in one backend: authenticated users work within role and resource scope, leads progress into validated requirements and quotations, accepted quotations create projects, projects progress through deliverables and lifecycle states, and delivered projects proceed through invoice generation, payment confirmation, and completion. MongoDB repositories provide indexes, conditional updates, controlled duplicate handling, and selected legacy compatibility while the service layer preserves the business rules.
